Output theo cấu trúc:

# 1. USER FLOWS
Với mỗi luồng chính (đăng nhập, luồng nghiệp vụ cốt lõi, ...), mô tả theo
bước: [Màn hình A] → hành động người dùng → [Màn hình B] → ...
Nêu rõ điểm người dùng có thể bối rối / cần feedback tức thời (loading,
error, empty state).

# 2. DANH SÁCH MÀN HÌNH (BẮT BUỘC — Architect sẽ dùng lại y nguyên danh
sách này, không tự nghĩ ra danh sách khác)
Liệt kê TẤT CẢ màn hình cần có, đúng format:
{số_thứ_tự}_{tên_file}|{tên_hiển_thị}|{Lý do UX ngắn gọn — màn này giải
quyết nhu cầu gì của user nào}
Ví dụ:
01_login|Đăng nhập|Điểm vào duy nhất, cần trạng thái lỗi rõ ràng khi sai mật khẩu
02_dashboard|Trang chính|Trả lời ngay câu hỏi "hôm nay tôi cần làm gì" cho user quay lại

Quy tắc:
- Mỗi dòng: {số_thứ_tự}_{tên_file}|{tên_hiển_thị}|{lý do UX}
- Tối thiểu 3 màn hình, tối đa 8
- tên_file: lowercase, underscore, không dấu

# 3. TRẠNG THÁI & EDGE CASE CẦN THIẾT KẾ
Với mỗi màn hình có rủi ro UX cao (form nhập liệu, luồng thanh toán, xoá dữ
liệu...): liệt kê trạng thái loading/empty/error/success cần có, và hành vi
mong đợi khi user thao tác sai.

# 4. GHI CHÚ CHO ARCHITECT
Những ràng buộc UX ảnh hưởng tới kiến trúc (vd: cần real-time update, cần
optimistic UI, cần phân trang vì danh sách dài) — Winston phải tính đến khi
thiết kế Data Model / API.
